# 远程插件模块化改造方案（对齐 DSH 插件设计规范）

> 2026-11-16。用户问题：`tools/dsh-plugin-smartquiz-remote/index.js` 单文件 **8190 行 / 411 KB**，
> 52 条路由、84 个顶层定义全在一个 `apply()` 闭包里；客户端 `client.js` 也单文件；
> 每次改动都要重启 DSH 才能生效，改一处得在八千行里翻。
>
> 本文先列**规范原文要点**（来自已安装版本 `dsh-doc` skill 的 `references/host-plugin.md`、
> `references/practices.md`），再对照本插件现状给差距，最后给分阶段抽取计划。

## 1. 规范要点（已安装版本原文归纳）

### 1.1 包与入口（host-plugin.md）

| 规范 | 原文要点 |
|---|---|
| Bundle | 包内 `dsh.bundle.patch` 指向 YAML patch，patch 里 `insert` 插件行 |
| Host 入口 | `index.js` 导出以下**二选一，不得混用**：`export function apply(ctx, config)`（可带 `inject`、`Config`）；或默认导出一个 service class |
| 注册方式 | 所有资源在 `apply` 内用 `ctx.effect` / `ctx.on` 注册并返回清理函数 |
| **Config** | 声明 `Config` 后，插件行的 `config` 在激活时被校验；**可调参数应放进 Config**，用户在 `cordis.patch.yml` 改，且该 patch 层能扛升级 |
| 文件清单 | patch、locale、detail 文档、icon、**以及每个运行时文件都要进 `files`**；新增模块/资源时必须同步更新 |
| 显示元数据 | `locale/*.json` 里的 `meta.title` / `meta.description` / `meta.detail`；icon 走 `./icon` 导出（或 package 顶层 `icon`），SVG/PNG/JPEG/WebP ≤256 KiB |
| **热更新语义（关键）** | "Installing a new bundle can activate through HMR; **replacing an installed package requires restart to load a fresh JavaScript module generation**." —— 改已安装包的 JS，本来就必须重启；这不是文件大小造成的 |

### 1.2 设计原则（practices.md）

1. **会话日志是唯一真相**，插件内存只是派生缓存；
2. **注册即 context 的 effect**：谁拥有 context 谁负责清理；跨 context（如 `agent.ctx`）注册要自己留 disposer；
3. **框架驱动、插件计算**：不要自己订阅 `session/event` 再全量扫描，应使用 `ctx.sessionProjections`（`apply(state,event)` 纯函数、忽略时返回同一引用、`stateVersion` 变更时升版本）；
4. **用最弱的扩展点**：`ctx.tools.restrict()` < `ctx.tools.guard()` < waterfall < `system-prompt/assemble`；
5. **不要用新 `type` 追加会话事件**（未知事件需 `ignorable: true`；`appendPluginRecord()` 仅供实验包，迁移时只尽力保留）；
6. **可调值进 Config**；
7. 性能：实时 token 用 `agent/assistant-stream`，等 `turn/end` / `assistant/message` / `tool/result` 等持久事件，**不要轮询 `agent/status`**；
8. UI：React slot + 主题 token `--dsw-alias-*`，**不要 iframe**，不要 `require` 客户端包；聊天行走 `ctx.uiConversation.events.register()` + `conversation.chat.node`。

## 2. 本插件对照规范的差距

| 规范要求 | 现状 | 差距 |
|---|---|---|
| `apply(ctx, config)` 单入口 | ✅ `export function apply` | 合规 |
| `Config` 声明 | ❌ 无 `export const Config`，直接用 `{...DEFAULTS, ...(config ?? {})}` | 配置无法在插件面板校验；`cordis.patch.yml` 里的键写错也没提示 |
| 运行时文件进 `files` | ❌ 无 `files` 字段 | 打包/发布时会漏 `lib/*.js`（linked 安装不受影响） |
| locale 元数据 | ⚠️ 只有 `package.json` 的 `meta.title/description`，无 `locale/*.json` | Plugin Manager 显示会回退，多语言缺失 |
| icon 导出 | ⚠️ 有 `icon.svg` 但未 `exports["./icon"]` | 面板可能用默认图 |
| 用 `ctx.sessionProjections` 派生状态 | ❌ 大量 `ctx.on('session/event')` + 自己维护 Map（`SUBAGENT_LAST`、`SESSION_BUSY`、`ANCHORS` 等） | 版本升级/回放时容易与日志不一致；但**改造量大**，列为远期 |
| 不轮询 `agent/status` | ⚠️ 子代理活动有 1.5s 轮询器（`SUBAGENT_POLL_MS`） | 规范建议改事件驱动（`subagent/*` 已可用），列为中期 |
| 可调值进 Config | ⚠️ `DEFAULTS` 有 20+ 项，但无 schema | 与 Config 缺口同源 |

## 3. 模块化目标结构

依赖方向严格单向：`index.js`（组装）→ `lib/*`（领域模块）→ `lib/util.js`（零依赖）。

├── index.js                 # 目标 ≤1500 行：DEFAULTS/Config、apply() 组装、路由注册表
├── lib/
│   ├── util.js              # ✅ 已抽：warnOnce / clientMsgDuplicated / abortError / originHash
│   ├── slots.js             # ✅ 已抽：SLOT_PRIORITY 及三个换算函数
│   ├── auth.js              # 待抽：令牌/设备/配对码/白名单/来源指纹（~500 行）
│   ├── http.js              # 待抽：route() 注册器、JSON 读写、caps 门、错误响应（~300 行）

抽取顺序按"依赖少、状态局部、测试可覆盖"排序（当前进度）：

1. ✅ `util.js` + `slots.js`（零依赖，已通过 4 个既有测试套件）
2. `http.js`（route 注册器与响应工具：纯函数化，不改业务）
3. `auth.js`（令牌/设备/白名单；有 `caps.test.mjs` 可回归）
4. `stream.js`（广播/连接表；`ws_frames.test.mjs` 回归）
5. `events.js` / `sessions.js` / `approvals.js` / `cli.js` / `tools.js` / `cards.js`
6. 收尾：`index.js` 只留组装；补 `Config`、`files`、locale、`./icon` 导出

## 4. 关于"改一行就要重启 DSH"

规范原文已经说明：**替换已安装包必须重启**才能载入新的 JS 模块世代（HMR 只对"新装 bundle/客户端插件"生效）。
所以模块化不能消除重启，但能带来三个实际收益：

1. **改动半径变小**：改甲板优先级只碰 `slots.js`（今天已抽），改鉴权只碰 `auth.js`；
2. **可独立验证**：每个 `lib/*.js` 都能被 `node --check` 与既有 `*.test.mjs` 直接覆盖，不必启动 DSH；
3. **可增量重启**：把"每次改都要重启"从"改 8000 行里任意一处"变成"改一个 200 行模块"，评审与回滚成本同步下降。

> 若将来要真正免重启：需要把易变逻辑放进**客户端插件**（HMR 生效）或做成"数据驱动"（配置/规则由 Config 提供），
> 而不是靠拆分 Host 文件。这条留作后续方向，不在本轮范围。

### 6.1 Client 两项已补齐（同日，第二轮收尾）

| 项 | 结论 | 证据 / 做法 |
|---|---|---|
| 主题 token | ✅ **已满足（且比硬编码更好）** | `client.js` 里**没有任何字面色值**（`#hex` / `rgb()` / `background` 全无），只用 `border: '1px solid currentColor'` 与继承文本色 —— 容器和控件完全跟随宿主主题，不会出现"抄错 token 名导致颜色不跟主题"的问题 |
