# 执行/编辑类卡片的显示设计与回传缺口（2026-11-16 审计）

> 触发：用户指出"有些具备执行/编辑功能的卡片（shell、python 等）显示设计有问题；
> 渲染失败没有回传，AI 会默认卡片正常显示"。

## 1. 现状：执行类工具有哪些卡、各自契约

| 卡片 | 类型名 | 源码契约键 | 显示什么 | 缺什么 |
|---|---|---|---|---|
| 工具调用行 | `tool_call` | `toolName` / `status` / `result`(或 `summary`) / `args` / `statusText` | 工具名 + 状态图标 + **单行摘要** | ❌ stdout/stderr/exitCode、耗时、可展开详情、取消入口 |
| 代码卡 | `code_card` | `code` / `language` / `status` / `title` | 代码 + 语言 + 状态 | ❌ **执行输出完全没有字段**（stdout/stderr/exitCode 无处可放） |
| 后台任务卡 | `job` | `cmd` / `job_id` / `status` / `title` | 命令 + 任务 id + 状态 | ❌ 输出/退出码、日志展开、终止按钮 |
| 应用卡 | `app_card` | `package` / `target` / `uri` / `params` / `message` / `title` | 跳转/启动 | — |
| 进度卡 | `progress_card` | `title` / `progress` / `description` / `status` | 进度条 + 状态 | ⚠ 只能被动显示，无回传 |

**结论（设计问题，按严重度）**：

1. **执行输出没有展示位**：`linux_shell` / `js_execute` / `python` 的 stdout、stderr、exitCode
   在卡片契约里**没有字段**，只剩 `ToolCallCardView.summarize()` 压成的单行摘要 → 出错时用户只看到
   "❌ 失败"，看不到哪一行报错。这是最实际的问题。
2. **失败无详情入口**：`tool_call` 渲染时**不附加 actions**，用户无法展开完整输出/复制错误。
3. **执行中不可取消**：`status=running` 只是文案；`tool_call` 没有 cancel 动作，与
   `UiActions`/工具取消能力脱节。
4. **状态更新依赖引擎推**：`canRender` 只要求 `toolName`，若引擎没推后续 `status`，
   卡片会永远停在"⏳ 执行中"。

## 2. 已经补上的：渲染失败回传 AI（2026-11-16，`fa16b9af`）

链路：`ComponentRegistry.render` 四条失败路径 → `RenderDiagnostics.record(类型, 原因, 需要字段)`
→ 下一次 `AIToolManager.executeTool` 结束时 `drain()` → 该次结果 `additionalInfo`
（`render_warnings` 列表 + `render_warning_text` 一句话）→ 模型下一轮可读。

真机自检（`--es mode render_feedback`）实测输出：
`上一步卡片渲染异常：卡片 table_card 渲染失败：数据与卡片契约不匹配（table_card 需要 align/headers/rows/title）`

## 3. 用户要求的第 2 项：注册期契约校验（做成"提示 + 交给 AI 判断"，不硬拦）

用户意见：`optXxx` 扫不出"必填"，**可以兜底**——返回错误信息让 AI 自己判断；
且部分工具（如 python）本身有解释器回传，硬校验会误杀。

### 设计

1. `CardContracts.overlap(type, keys)`：返回该卡片契约与传入字段的交集；
2. `ui_component validate` / `create` 返回里增加 **非阻断** 字段：
   ```json
   "contract_warnings": [
     {"card": "table_card", "given": ["rows"], "expected": ["align","headers","rows","title"],
      "message": "table_card 至少需要 headers/rows 才能渲染成表格，你只给了 rows；如需按兜底显示可忽略本提示"}
   ]
   ```
3. 判定规则（避免误杀）：
   - 只在该卡有契约、且 `render.props` 非空、且**交集为空**时提示；
   - 永远不阻止注册/创建（`validate` 的 problems 里不放它，单独的 `contract_warnings`）；
   - 工具结果里同时说明"可忽略"，让模型自行决定（用户原话：让 AI 自己判断）。
4. 与渲染期诊断互补：注册期提示是"事前预防"，`RenderDiagnostics` 是"事后回传"。

## 4. 用户要求的第 3 项：交互控件回传（get_result）

现状：动态组件走 `render.card` **只能展示**；`primitive_slider_range` 画得出双滑条，
但拖动结果没有回传通道。`ui_component get_result` 只对 `NativeLayoutRenderer` 的
`input/slider/switch` 节点生效（那条路有 `ComponentActions` 回调）。

### 需要的改动（跨 4 处）

1. `ComponentData` 增加 `componentId`（动态组件创建时写入）；
2. `ComponentRegistry.render` 把 componentId 透给卡片；交互类卡片（slider/toggle/tag_input/
   checkbox_group/rating/stepper）在值变化时调用 `ComponentActions.submit(componentId, value)`；
3. `ComponentActions` 把值写进组件注册表（`get_result` 的同一份存储）；
4. `ui_component get_result` 增加 `wait_seconds` 语义（已有），返回 `{value, field}`。

### 验收

真机：创建含 `primitive_slider_range` 的动态组件 → 拖动 → 另一侧 `get_result` 拿到数值；
单测：`ComponentData` 带 componentId 时回调路径正确、无 id 时不崩。

## 5. 建议顺序

| 顺序 | 项 | 理由 |
|---|---|---|
| 1 | 执行类卡片补 `stdout/stderr/exitCode` + 失败可展开 | 用户实际痛点（看不到报错） |
| 2 | 第 2 项：`contract_warnings` 非阻断提示 | 小改动、零误杀，与回传互补 |
| 3 | 第 3 项：交互回传 | 架构改动，单独一轮 |

## 7. 第 3 项（交互回传）核查结论（2026-11-16 真机）

**关键发现：`primitive_*` 类卡片是"聊天流只读卡"，根本没有 component_id。**

真机实测（`--es mode input_feedback`）：
```
INPUT_CREATE={component_type=primitive_slider_range,
  message=组件已加入聊天流: primitive_slider_range（只读展示卡片：不支持 update/close/get_result…）}
INPUT_FEEDBACK={result=not_found, message=组件不存在: null, success=false}
```

原因：`SystemUIComponentTool` 把 `chat_` 前缀的 id 判为只读（`isChatStreamCardId`），
而 primitive 卡片创建时直接进聊天流，不分配 component_id —— 所以无论有没有 collector，
`get_result` 都取不到。

**官方可交互容器是 `layout_canvas`**（已实测通过）：
```
INPUT_CREATE={component_id=comp_1794775762087_8521, type=layout_canvas, success=true}
INPUT_FEEDBACK={result=pending, component_id=comp_1794775762087_8521,
  message=UI 动作已执行: get_component_result, success=true}
```
`pending` 是正确语义：等待用户操作。`LayoutCardView` 会为带 `key` 的输入控件注册
collector，`PrimitiveInputCollector` 是本轮给 primitive 路径补的同类能力（供将来
primitive 若支持 componentId 时直接生效）。

### 结论与建议

| 场景 | 是否支持 get_result | 说明 |
|---|---|---|
| `layout_canvas` + `slider_range/toggle/input`（带 key） | ✅ 支持 | 推荐路径，已实测链路可达 |
| `primitive_slider_range` 等 `primitive_*` | ❌ 不支持 | 聊天流只读卡，无 component_id |
| 插件 `render.card` 指向 primitive_* | ❌ 同样只读 | 同上 |

**下一步（若要"动态组件能收集输入"）**：应在 `SystemUIComponentTool.create` 里把
交互类 primitive（slider_range/toggle/checkbox_group/rating/stepper/tag_input）走
"可交互组件"分支（分配 component_id + 挂 collector），而不是进聊天流；这属于行为变更，
需要单独评估对既有只读用法的影响。

## 8. 第 3 项收口：值确实回传了（2026-11-16 真机）

按"给缺通道的卡加键"的思路，在 layout_canvas 里加一个按钮节点作为提交通道：

```json
{"type":"column","children":[
  {"type":"text","text":"交互回传自检"},
  {"type":"slider_range","key":"amount","min":0,"max":100,"values":[20,80]},
  {"type":"toggle","key":"auto","label":"自动"},
  {"type":"button","text":"提交","action":"submit"}
]}
```

真机 `get_result` 实测：
```
{"action":"submit","values":{"amount":"{\"low\":56,\"high\":100}","auto":""}}
```

即：**控件值被收集并随 action 一起回传**（`amount` 是拖动后的值，键名来自节点 `key`）。

结论：
- 有 `key` 的输入控件 + 任意一个 action（按钮）→ `get_result` 就能拿到 `{action, values}`；
- 没有按钮的纯展示卡 → `pending`（正确语义：等用户操作，但没有可提交通道）；
- `primitive_*` 聊天流只读卡仍不支持（无 component_id），需要按钮通道时用 layout_canvas。

**因此"缺回传/点击通道的卡片"的统一解法就是：加一个带 key 的按钮节点**，不需要改卡片组件模型。
