## 二·五、渲染引擎盘点（实测）

### 实际形态：一套自研 View 体系 + 4 条内容通道

**不是单一渲染引擎。**

| 引擎 | 位置 | 规模 | 负责 |
|---|---|---|---|
| Android View（Java） | `ai/chat/component/` | 36 个 \*CardView（component 包 68 个类）、243 个 XML | 所有卡片骨架 |
| 声明式 layout | `NativeLayoutRenderer` | **4296 行 / 95 个控件 type（113 个 case 分支）** | JSON → 原生 View |
| Canvas 自绘 | `ChartCardView.onDraw` | 735 行 | 全部图表（无第三方库） |
| WebView | `HtmlCardView` + `HtmlSandbox` | — | HTML 富内容、网页卡 |
| Markwon | MarkdownCardView 等 | — | Markdown → Spannable |
| Compose | 1 处 import | ≈0 | — |

**真正算“渲染引擎”的只有 `NativeLayoutRenderer`**，其余是原生组件与内容渲染通道。

### NativeLayoutRenderer 的控件能力

- **布局**：column / row / scroll / card / wrap / grid / space / tabs / stack / accordion / carousel
- **数据**：table / steps / timeline / stat / progress_ring
- **图表**：line_chart / bar_chart / pie_chart / sparkline
- **输入**：input / number / password / multiline / otp / email / tel / url / search_bar / tag_input / slider
- **选择**：select / switch / checkbox_group / radio_group / date / time / datetime / color / rating / toggle / dropdown / stepper / slider_range
- **媒体**：image / video / audio / html / qrcode / barcode / countdown / calendar
- **交互**：button / link / progress / spinner / marquee / badge / avatar / quote / code / icon
- **装饰**：divider / divider_v / separator

### 已有的组件层（这块是对的）

`ComponentRegistry`（439 行）/ `ComponentTypes`（417 行）/ `ComponentTheme` / `ComponentLifecycle` / `ComponentDisplay` / `CardShell`
—— 注册、类型、主题、生命周期齐全，正是组件库该有的结构。

### 核心问题：双轨重复

同一语义存在两条渲染路径：

```
ui_component(component_type=table)  → TableCardView            （Java 手写）
ui_component(component_type=layout) → NativeLayoutRenderer → table 分支  （JSON 驱动）
```

已知重叠（至少）：`table` / `chart` / `steps` / `alert` / `list` / `note` / `info`。
**后果：视觉规则与适配逻辑各维护一份，改一处另一处不跟随。** 这是“适配工作量大”的主要来源之一。

### 收敛判断规则

- **需要复杂交互或高性能**（video / audio / chart / qrcode）→ 保留专用 CardView
- **纯组合类**（info / note / alert / steps / list）→ 收敛到 layout，删掉专用 CardView

收敛后，“适配”从改两处变改一处，预览台也只需做一个。

> **【v1.1 补充】这里有个被漏掉的兼容缺口，必须先解。**
>
> 上面写「纯组合类 → 收敛到 layout，删掉专用 CardView」，但聊天流里**已经落库的消息**存的是 `component_type + props`，而 `ComponentRegistry`（439 行）/ `ComponentTypes`（417 行）/ 8 个 PartRenderer 都是按 type 分派的。**直接删掉 `TableCardView` 这类实现，历史消息就是白屏或降级占位**——而聊天页是最高频界面，等于把一次重构变成一次数据兼容事故。
>
> 正确顺序：
>
> 1. 先建一张 **`component_type → 渲染器` 映射表**，带 `v` 版本（`{"table":{"v":1,"impl":"layout","spec":{...}}}`）
> 2. 新 type 直接指向 layout 等价物；老 type 保留一条 **兼容渲染**路径（内部转成 layout JSON 再渲染一次即可，**不要**维护第二套视觉代码）
> 3. 用埋点/日志确认库内不再出现老 type 的真实流量后，才删 CardView
>
> 这张映射表与 五·三 的「权威实现表」**是同一张表**，合并维护，别做两份。

### 缺失：NativeLayoutRenderer 没有可视化预览入口

4296 行手写解析器，加一个控件要同时改多个分支；改 JSON 只能跑 App 看效果。

已有 `DebugLayoutInjectActivity` 可通过 adb 注入 layout JSON（见二·八），但只到「命令行 + 手工转义」这一层，缺少样例列表与即时编辑。**这是当前成本最高的单点。**

## 二·六、样式库盘点与收敛

### 现状：历史叠加，未收敛

**一、颜色有 4 套来源**

| 来源 | 规模 | 例子 |
|---|---|---|
| `res/values/colors.xml` | 379 行 / 313 个色值 | 静态色值 |
| `ComponentColors` | 15 个方法 | `textPrimary` `accent` `chartColor` |
| `ComponentTheme` | 12 个方法 | `surface` `outline` `brand` `cardBackground` |
| `theme/` 包 + M3 HCT | 动态取色 | `ThemeColors` `ThemeSkin` `ThemePreset` |

同一个“主色”可能取到四个不同值；`ComponentColors.accent()` 与 `ComponentTheme.brand()` 大概率是同一语义的两个名字。

**二、尺寸 token 严重不足**

`dimens.xml` 有 **192 行、182 个 dimen**，但绝大多数是机械档位（`spacing_8/12/16`、`elev_0..16`、`max_*/min_*`、`chat_v2_*`），缺的是「语义化间距/字号档」：

```
spacing_8 / spacing_12 / spacing_16 = 8 / 12 / 16dp
button_height_small = 36dp
card_shell_radius / padding / border / gap = 14 / 14 / 1 / 10dp
card_shell_header/meta/body/action_text = 13 / 11 / 13 / 12sp
（无 text_size_* 语义字号档；spacing_small/normal/large 这套命名并不存在）
```

而代码里有 **1153 处 `dp(数字)` 内联值**。原因：这套 token 服务的是「页面级布局」（24dp、32dp），卡片内部的 6/10/16dp 不在其中，只能硬编码。

**三、字号两套**

- `dimens.xml` 的 `text_size_*`（14/16/18/20）
- `ComponentTheme` 的 `headerTextSize / metaTextSize / bodyTextSize / actionTextSize`

**四、静态样式与代码样式分裂**

`styles.xml`（580 行 / 65 个 style）管 XML 里的控件，`ComponentTheme` 管代码创建的控件。同一个按钮，来源不同、样式来源也不同。

### 诊断

“适配工作量大”有很大一部分来自**样式没有单一可信来源**。
1153 处内联尺寸 + 4 套颜色 → 「统一收紧间距」「全局换主色」这类需求只能靠人工搜索替换。

### 收敛路径（按顺序，代价递增）

1. **定唯一入口**：选 `ComponentTheme`（已在 21 个文件使用，最靠近组件层），其余向它收
2. **`colors.xml` 降级为原始色板**：只放 palette，语义色全走 `ComponentTheme`
3. **`ThemeColors` / HCT 作输入**：动态取色算出结果后喂给 `ComponentTheme`，禁止组件直接读
4. **`dimens` 只管布局级常量**，组件内部一律 `ComponentTheme.space(SM/MD/LG)`
5. **机器守规矩**（v1.1 改写，原为「立规矩」）：新代码禁止 `R.color.xxx` 与 `dp(字面量)`。

   ⚠️ 这一条**不能靠 code review 守**：1026 个 Java 文件、1153 处内联值、只有 21 个文件在用 `ComponentTheme`，靠人盯必然破防。改为机器守：

   - 写两个自定义 Lint 规则：`AvoidRawColorRes`（组件层禁止直接 `R.color.*`）、`AvoidInlineDim`（禁止 `dp(字面量)`）
   - 存量文件先 `@Suppress` 白名单冻结，**新代码命中即 warning，CI 对新文件设为 error**
   - 成本约一天，比「定规矩 + 开会强调」有效一个量级

   同理，二·九 那 6 个问题里**「debug 下缺 attr 直接抛」是最关键的一条**——它把静默 bug 变成崩溃，是唯一能自动暴露主题断层的手段，本身也是一种"机器守"。

### 前置条件

第 4 步要先补档位：现在只有一个 `padding()`，需拆成 `space(SM/MD/LG)` 与多档字号，否则无法替换那 1153 处内联值。

### 目标状态

```
色板(palette) → 动态取色(HCT) → 语义色(ComponentTheme) → 组件
布局常量(dimens) ─────┐
                      └→ 间距档位(ComponentTheme.space) → 组件
```

组件层只认 `ComponentTheme` 一个入口。

## 二·七、动效盘点

### 现状：全手写，缺 token

| 动画手段 | 用量 |
|---|---|
| `ObjectAnimator` | 11 处 |
| `animate()`（ViewPropertyAnimator） | 24 处 |
| `ValueAnimator` | 20 处 |
| `TransitionManager` | 1 处 |
| **`LottieAnimationView`** | **0 处** |
| `MotionLayout` | 0 处 |
| `Choreographer` | 0 处 |

资源：`res/anim` 9 个、`res/animator` 1 个。

**Lottie 6.4 已引入但零使用**——与 Compose 同源问题：依赖齐全，没有落地。

### 缺什么：motion token

动效全部是系统 API 手写（11 + 20 + 24 = 55 处），没有统一约束：

- 时长各处不同，无法表达「所有卡片进场都是 200ms」
- 缓动曲线散落，每处 `new DecelerateInterpolator()` 各写各的
- 同一个交互在不同卡片里表现不一致

**这是样式库缺口的同类问题**：样式缺尺寸/颜色 token，动效缺**时长/曲线 token**。

### 目标

```java
// 现在
anim.setDuration(180);
anim.setInterpolator(new DecelerateInterpolator());

// 目标
anim.setDuration(Motion.DURATION.medium);
anim.setInterpolator(Motion.EASING.standard);
```

Motion token 两维：

- **时长**：`short` / `medium` / `long`
- **曲线**：`standard` / `decelerate` / `emphasize`

### 场景分工（别混用）

| 场景 | 用什么 |
|---|---|
| 属性过渡（透明度、位移、缩放） | ViewPropertyAnimator + Motion token |
| 状态切换（展开、折叠、替换） | Compose `AnimatedVisibility` / `animate*AsState`（依赖已在） |
| 复杂矢量动画（加载、成功、插画） | Lottie（已引入，启用即可） |
| 手势驱动的连续动画 | 手写 ValueAnimator（确实无法用库替代） |

### 与样式库合并改造

Motion token 与样式 token 属于同一类改动，**可合并为一次改造**，增量成本很低。

## 二·九、主题系统诊断

### 现状：已经重构过，机制是完整的

`ThemeManager`（450 行）负责：

- 深浅三档（浅色/深色/跟随系统）→ `AppCompatDelegate` + DayNight
- 主题色：**7 个预设 + 自定义色**，基于 MCU HCT 色板
- 全局注入 ThemeOverlay（`Application.onActivityPreCreated`，在 `setContentView` 之前生效，切换即时）
- 皮肤包（`standard` / `military` / …）
- 变更监听 `OnThemeChangedListener`（供 Compose / Service / 运行中组件）

资源侧：`theme_overlays.xml`（values + values-night）+ `theme_overlay_dynamic.xml`，**31 档 overlay**（7 预设 + 24 色相），由 `tools/GenOverlays.java` 生成。

`ThemeColors`（116 行）有两条取色路径：

- `get(resId)`：读 `hc_*` 资源 → **只适配深浅色**
- `attr(context, attrId)`：读 `?attr/colorXxx` → **跟随换肤**

### 问题 1：主题覆盖靠白名单（最严重）

`ThemeColors.get(context, resId)` 用一串 `if` 把特定 resId 映射到 attr：

```java
if (resId == R.color.primary || resId == R.color.primary_color)
    return attr(context, R.attr.colorPrimary);
if (resId == R.color.primary_dark) ...
```

**没被枚举到的颜色“原样返回”，即不跟随换肤。** 新增语义色时容易漏，且不报错——表现为「换主题后某个角落颜色不对」，极难定位。

### 问题 2：静默回退掩盖断层

`ComponentTheme` 有 **8 处 `orFallback(attr(...), ComponentColors.xxx())`**：attr 解析失败就退到第二色源，不告警。主题断层因此长期不可见。

### 问题 3：自定义色精度不足

自定义色就近映射到 **24 个 15° 色相**之一，用户选的颜色与实际显示存在偏差，UI 上也没有提示。

### 问题 4：资源膨胀

31 档 × 浅/深 = **62 套 ThemeOverlay**，每套重定义整套颜色属性，编译期与包体都有成本。

### 问题 5：两个 `get()` 语义不同

- `get(resId)`：只适配深浅色
- `get(context, resId)`：跟随换肤

同名不同义，很容易在组件里误用前者，导致换肤不生效。

### 问题 6：命名族跨两处（原判断“注释漂移”不成立）

`ComponentTheme` 注释称“尺寸口径来自 `res/values/dimens.xml` 的 `card_shell_*`”——**这句是对的**：`dimens.xml:139-148` 里确有 10 个 `card_shell_*`（radius / padding / border / gap / header_text / meta_text / body_text / action_text / action_min_height / body_max_height）。

真正的隐患是**前缀被两类资源复用**：`strings.xml` 里另有 5 条 `card_shell_more / empty / loading / error / truncated` 文案。同名族跨文件与跨资源类型，全库搜索 `card_shell_*` 会同时命中这两类，改尺寸时容易看串。

### 建议

1. **组件层禁止白名单**：统一走 `attr`，缺 attr 视为错误（debug 下直接抛）
2. **去掉静默 fallback**：debug 版 attr 失败就报错，不再退到第二色源
3. **自定义色改为真 HCT 生成**，或明确标注「近似色」
4. **评估 overlay 数量**：24 色相档是否可降为 12 档，或改运行时着色
5. **合并两个 `get()`**：语义只保留一个入口，避免误用
6. **修正注释漂移**

## 三、Dart / Flutter 评估

### 3.1 为什么直觉上想用 Dart

- Flutter 开箱即用的 Material 3 组件、动效、统一主题
- 热重载，改完秒看
- 声明式写法比 Java View 清爽

### 3.2 为什么最终不建议

| 代价 | 说明 |
|---|---|
| 运行时 | 每个 ABI +8~10 MB，独立 UI 线程与内存 |
| 动态性 | Flutter 是 AOT，组件逻辑改一次就得发版；JSON DSL 可以服务端下发、实时 patch |
| 复用 | Flutter Web 是 Canvas 自绘，与现有 React/DOM 面板互不相通 |
| 原生性 | Flutter 画出来的不是系统控件；用户明确要求“使用原生控件” |
| 重写量 | 8 个 renderer + 255 个布局要重来一遍 |

### 3.3 如果非要用 Dart（仅记录，不采用）

唯一可行的嵌入形态是 **add-to-app**：`flutter create -t module` → `settings.gradle` 挂载 → `implementation project(':flutter')` → `FlutterActivity` / `FlutterView`。

且必须遵守：**一个画布一个 FlutterView**，绝不能按组件粒度起实例（每个实例都是一个引擎）。消息流里用 `FlutterEngineGroup` 也要限制并发数并做可见性回收。

### 3.4 Dart 的三个诉求，Compose 逐条接住了吗（v1.1 新增）

3.2 只论证了 Flutter 的代价，却没回答「那这三个诉求由谁来解决」。缺这一张表，整个决策读起来像**回避问题**，而不是解决它：

| Dart 的诉求 | Compose 的答案 | 证据 / 依赖 |
|---|---|---|
| 开箱即用的 Material 3 组件 | material3 + `compose-bom:2024.02.02` **已在 gradle，零新增依赖** | 见 2.2 |
| 热重载，改完秒看 | AS Compose Live Edit + `@Preview`，能覆盖「改完秒看」的绝大部分场景 | **依赖预览台**（七章梯队 1） |
| 声明式写法比 Java View 清爽 | 同一份 layout JSON，Compose 渲染器就是一个 `@Composable` 函数，体量比 4296 行 `NativeLayoutRenderer` 小一个量级 | 需先跑通 5 个控件试点 |

**结论改写**：不是"绕开 Dart"，而是**用更便宜的路径拿到同样三个好处，且不放弃原生控件与 JSON 动态性**。这比单纯论证 Flutter 的坏处更有说服力。

## 四、调试与适配：真正的问题

### 4.1 调试难

链路是「改代码 → 编译 → 装包 → 造一条带该 part 的消息 → 看效果」。
根因不是语言，是**缺预览台**（`util/preview` 是空的）。

### 4.2 适配累

根因是**样式散在每个 renderer 里**：颜色/字号/间距各自硬编码，改一处要翻十几个文件。

### 4.3 解法（按性价比）

1. **预览台**：debug-only Activity，遍历所有已注册 kind，各喂一份固定 Part，直接渲染
2. **theme token 收敛**：`spacing / typeScale / radius` 三组，renderer 只取 token
3. **抽 build/bind/relayout 协议**：沿用 `HTML_DESIGN_RULES.md` 里“表盘外置协议”的思路
   （`build(host)` / `paint(n,S)` / `relayout()`），把“重排”从每个 renderer 收口到一次

## 五、推荐架构：JSON 契约 + 双渲染器

### 5.1 核心思路

**layout JSON 是数据契约，渲染器是可替换的实现。**

```
layout JSON ──┬── Java View 渲染器（老控件，冻结后逐步淘汰）
              └── Compose 渲染器（新控件，Material 3 + 可预览）
```

### 5.2 三条硬约束

1. **JSON 写语义，不写像素**
   - ✗ `{"color":"#FF5722","size":14,"margin":12}`
   - ✓ `{"variant":"body","tone":"danger","space":"md"}`
2. **能力显式声明**：`{"capabilities":["scroll","snap"]}`，不支持的渲染器降级为占位而非画错
3. **带 schema version + 未知 type 降级**：`"v":2`，不认识的 type 跳过并留可见占位

### 5.3 维护铁律

> **同一个控件只能有一个“权威实现”。**

Compose 接管 `card` 后，Java 那套冻结、最终删除。不允许两套都“能用、看情况走哪个”——半年后必分叉，排障成本比现在高十倍。

建议在规范文档开头加一张表：控件名 / 权威渲染器 / 另一套状态（冻结｜待删｜只读）。

### 5.4 不要追求像素一致

多渲染器只能保证**语义一致**（信息层级、交互含义），不可能像素一致。
验证方式：黄金样例——每个控件固定一份 JSON，各自出截图人工复核一次。

## 五·五、事件驱动的插槽设计

### 现状（实测）

当前实现是 `setTag("xxx_slot")` + `findViewWithTag` 做动态挂载：

```
agent_summary_slot / tool_distribution_slot / tool_params_slot
tool_retry_slot / tool_edit_slot / agent_progress_slot / image_grid_slot
（实测 `setTag("*_slot")` 11 处、`findViewWithTag` 20 处）
```

**优点**：局部替换，不重建整行，比 `notifyItemChanged` 整行刷新省。
**问题**：字符串魔法（拼错即静默不显示）、重复挂载、清理靠手动 `clearXXXSlot`、难测试。

### 目标：插槽声明化

把「位置 / 内容 / 清理」全部从代码搬到数据里。

**layout 里声明占位：**

```json
{"type":"card","title":"shell_command","children":[
  {"type":"text","text":"运行中…"},
  {"type":"slot","id":"tool_params"}
]}
```

**事件只带 slotId 和片段：**

```json
{"slot":"tool_params",
 "layout":{"type":"table","headers":["参数","值"],"rows":[...]}}
```

渲染器找到 `tool_params` 占位节点，用片段替换。不再需要 `setTag` / `findViewWithTag` / 手写 clear。

### 升级顺序（代价很小）

1. **tag 字符串收敛成常量或枚举**——半天，零风险，先做
2. **slot 显式生命周期**：`mount / update / clear` 三个动作，替代「有就删、没就建」的隐式规则
3. **引入 `{"type":"slot","id":...}` 节点类型**，让 layout 描述骨架

### 必须防的坑

RecyclerView 复用时，slot 内容残留会串行——第 5 条消息的 `tool_retry_slot` 出现在第 8 条上。
**规则：bind 必须幂等。** 每次 bind 按数据重建 slot，而不是依赖手动 clear。

### 与事件转换器的衔接

完整链路应为：

```
SSE 事件 → reducer → 状态（含 slot 数据）→ layout JSON → 渲染器装配 slot
```

而不是现在的「事件 → 手工 new View → setTag 挂上去」。

## 五·六、渲染器契约（v1.2 新增，客户端侧）

> **这节的定位**：五·五 定的是「链路形状」，这节定的是「链路上流动的数据长什么样」。
>
> 服务端侧有独立的**《服务端更新指南》**管「发什么、怎么发、什么时候能改」，不在本文档范围内。
> **本节只管客户端这一侧**：收到什么形状的数据、用什么键去重与排序、认不出的类型怎么办、超出的情况怎么降级。
>
> 前提已定：采用**服务端下发动态 UI**，新增类别只更新服务端插件，客户端不发版。这个前提把风险位置彻底改变了，见下。

### 一、前提变了：客户端只剩一件不能远程修复的东西

「改服务端插件就能修」只覆盖数据层，覆盖不到渲染器本身：

| 错了什么 | 改服务端插件能救？ | 后果 |
|---|---|---|
| UI 定义写错（顺序、文案、字段缺失） | ✅ 能 | 下次下发即生效 |
| 渲染器表达力不够（新结构画不出） | ❌ 不能 | 空白或难看，只能发版 |
| 渲染器 bug（崩溃、绘制错乱） | ❌ 不能 | 已装老客户端长期带病 |
| 未知节点没有降级路径 | ❌ 不能 | 整条消息消失 |

**结论：渲染器是整个系统里唯一不可远程修复的部分。**

所以本节的约束核心不是「功能多」，而是**渲染器要薄、认不出也不出事**。这与 五·三 的「同一控件只能有一个权威实现」是同一条铁律的两面：前者管「不要有两份实现」，这里管「唯一那份不能太重」。

### 二、三个键，各管一件事（不许越界）

链路里的数据带三种键，职责必须分清，混用必出 bug：

| 键 | 解决什么 | 为什么不能用别的替代 |
|---|---|---|
| **id**（持久、全局唯一） | 去重/幂等、归属哪条消息、DiffUtil 稳定 key、恢复历史会话 | 不能用 order 代：order 不唯一，认不出「同一条」 |
| **order**（整数，服务端权威） | 排列顺序 | **不能用 id 代：唯一 ≠ 有序**，UUID 排不了序 |
| **形状**（类型 → Merge 语义） | 决定新包是覆盖还是追加、能否边流边显 | 推不出来，必须查表 |

**铁律：永远不要写 `sortedBy { it.id }`。** 这条要在 code review 里拦住——它看起来像「按 id 排序」，实际是把随机值当顺序用，出错时表现为 part 乱序且难以复现。

**id 的附带好处（值得利用）**：持久唯一意味着去重不需要额外的 `Set` 去重窗口（那个集合会无限增长）。直接 `indexOfFirst { it.id == partId }` 即可，重启后依然有效。

**但「已存在」不等于「忽略」**——这是最容易写错的一处。`dsh_command` 从 running 变 done，必然是同一个 id 再推一次；写成「存在就 return state」，进度条会永远转圈。必须逐形状定义合并规则（见第四节）。

### 三、流式 part 的状态机：拼接未完成绝不解析

`tool_call` 的 arguments 是 JSON **分片**流式到达的，中途任何一片单独 `parse` 必然失败。表现为偶发「工具调用参数解析错误」，且只在慢网下复现。

```
pending → streaming（只 append 字符串，不解析、不渲染内容） → complete（才 parse + 渲染）
```

`streaming` 阶段**只显示「调用中…」**，不要试图渲染半截 JSON。同一规则适用于所有流式类型：**按形状决定「能否增量显示」，不要统一处理**——这正是 part 渲染相对通用渲染器的优势所在。

### 四、按形状归并：100+ 类别 → 8 种形态

类别有 100 多种，但 UI 形态只有几种。**按形状写规则，不按类型写分支**，否则 100+ 分支既写不完也改不动。

| 形状（Merge 语义） | 渲染原语 | 允许边流边显 | 同类合并规则 |
|---|---|---|---|
| 单值覆盖：状态 + 一段文本 | text 卡 | ✅ | `copy(content = new)` 覆盖 |
| 流式追加：不断 append | text 卡（流式变体） | ✅ | `args + delta` 追加 |
| 一次性生效：首包定终局 | result 卡 | ❌ | 非空则保留，`if (empty) copy(...)` |
| 进度/计数：有数值区间 | progress 卡 | ✅ | 覆盖 status/progress |
| 键值对：字段集合固定 | info 卡 | ❌ | 覆盖整组字段 |
| 列表：可变长度 entries | list 卡 | ✅ | 按 entry id upsert |
| 树状：可嵌套子节点 | 递归渲染 | ❌ | 递归 merge（唯一需要递归的） |
| 未知：客户端不认识 | 降级文本 + 小标记 | — | 整包覆盖（见第五节） |

**分派用注册表，不用 `when` 写 100 个分支：**

```kotlin
object PartShapeRegistry {
    private val byType = HashMap<String, ShapeHandler>()   // 类别 → 形状处理器
    fun of(type: String): ShapeHandler = byType[type] ?: UnknownHandler
}
```

理由：`when` 分支非 sealed，编译期查不出漏类型，且新增一类要改 3 处（分派、merge、render）；注册表只改 1 处——这正好对应 七·五 那条判据「新增控件改动文件数 ≥5 → 1」。

**关键提醒：100+ 类别 ≠ 100+ 个 Composable。** 若一类对应一个组件，就等于把「按卡片迁移 40+ 个」放大到 100+ 次，必然写不完。顺序必须是 `原语先 Compose 化 → 各类别映射到少数原语组合 → 加一类只加映射，不加组件`。这也是 `weather_card` 不适合当试点的原因：做完仍是 1/100，底座还是 CardView。

### 五、兜底降级：宁可难看，不可消失

100+ 类别 + 服务端可随时新增 ⇒ **必然出现「服务端发 103 类、客户端只认 100 类」的版本错位**。这不是异常，是常态设计。四条约定：

1. **未知类型必须显示，不能崩也不能静默丢。** 降级为「未识别: xxx_type」+ 原始内容片段（可折叠），并带上原始 JSON 便于反馈时定位。
   - 抛异常 → 整条消息 bind 断掉，整个列表空白（最糟）
   - 静默丢弃 → 内容无故消失，比崩更难查
2. **兜底统一按「整包覆盖」处理。** 降级卡不知道那一类后续是追加还是覆盖；若按追加累积会越堆越乱。整包覆盖最多是内容不完整，而「不完整」比「错乱」好判断。
3. **认不出的组合容器 → 按默认垂直布局把子节点画出来。** 新结构的组合容器在老客户端上应退化成「排版不对但内容齐全」，不能整块空。
4. **白名单只增不删。** 已下发过的节点永远保留渲染能力；废弃只标记 deprecated，不删。因为老客户端会一直存在，而「曾经下发过哪些节点」无法可靠清账——收缩等于在不知情的情况下炸一批设备。

**打点（兜底越顺，越需要观测）**：兜底不报错，所以新类型可能长期停在降级态而无人发现。埋三个计数并在 debug 面板可见：

| 指标 | 说明 |
|---|---|
| 未知类型命中率 | **最重要的健康指标**，直接反映线上版本错位程度；持续上涨=该评估发版 |
| 重复 id 命中次数 | 去重生效频率，反映重连频率 |
| 排序等待超时次数 | 校验器放弃等待、放行乱序的次数 |

三者交叉才有意义：如「重复高 + 未知低」= 重连频繁但版本正常。

### 六、骨架与内容必须分离

服务端下发的是**骨架**（有哪些 slot、什么顺序、什么组件），事件流填的是**内容**。

- 骨架按 hash 缓存，内容走增量
- 两条路径不能合并：否则每输出一包就要重下一次完整 UI，流式输出变成整卡重绘，滚动位置乱跳

这条与 五·五 的 `{"type":"slot","id":...}` 是同一个设计：**骨架描述「位置」，事件只送「片段」**。

### 七、本节验收判据（与 七·五 合并执行）

| 判据 | 怎么测 |
|---|---|
| `sortedBy { it.id }` 与「按 id 排序」注释 | `git grep` = 0 |
| 新增一个类别需要改的文件数 | **= 1**（注册表一行映射），拿一个真实新类别演练 |
| 未知类型事件 | 造一条假 type 的事件，**不崩、不空白、可见降级卡** |
| 半截 JSON 分片 | 把 `tool_call` 参数拆成 3 片投递，**无解析错误、无半截渲染** |
| 重连重放同一批事件（乱序 + 重复） | 去重后 part 数量正确、顺序正确、不重复不丢 |
| 长对话 500 条滚动 | 无闪烁、无滚动位置回跳（依赖 id 作稳定 key） |

### 八、待确认（影响实现方式，非阻塞）

1. **`order` 的权威来源**：是服务端在 part 上直接给整数字段，还是靠「到达校验器」保证有序？**若是后者，需明确校验器超时放行时的排序退化策略**（建议：超时后按 arrivalIndex 追加，并打点）。
2. **100+ 类别是扁平一串，还是带层级前缀**（如 `tool.*` / `msg.*` / `sys.*`）？若带前缀，注册表可按组注册默认形状，只有例外单独注册，代码量与未知类型命中率都会明显下降；若扁平，建议本地先建「类别 → 形状」静态映射把扁平还原成分组。
3. **四类事件是互斥平铺，还是可嵌套**（`tool_result` 内是否还能含文本片段）？平铺用 `List<Part>`，嵌套需递归投影，本地模型差别很大，越晚改代价越高。

### 九、小结：客户端这一层能软到什么程度（v1.3 补充）

> 本节是 五·六 的收口，也是**给 dsh 电脑端对接方看的一页**。前八节讲「怎么实现」，本节只讲「边界在哪、谁负责什么」。

#### 9.1 一句话结论

**能远程改的只有「选择」，改不了「绘制」。**

服务端可以决定「用哪个原语、什么顺序、什么样式」；「这个原语怎么画」永远留在 APK 里。所以真正的边界不是「软不软」，而是——**原语一经发出即为永久契约：只能增，不能改，不能删。**

#### 9.2 软度定档

| 档 | 服务端能改什么 | 仍需发版的情形 |
|---|---|---|
| 0 硬编码 | 无 | 任何改动 |
| 1 映射表 | 类别 → 形状的对应 | 需要新形状时 |
| 2 配置表 | 映射 + 样式 token + 策略开关 | 超出 token 表达力时 |
| **3 SDUI（本轮选定）** | **控件树：选原语、定顺序、给样式** | **需要新原语时** |
| 4 表达式 / 脚本 | 连逻辑都能下发 | 不建议：稳定性不可控 |

选 3 档的代价已经明确：原语是唯一发不了补丁的地方（见 五·六 开篇）。因此原语总量压在 **10 个量级**，宁可不够用，也不要多——多一个就是一份不能还的技术债。

#### 9.3 动态字段：分两类，只有一类自由

| 字段类别 | 例子 | 老客户端忽略的后果 | 是否允许自由扩展 |
|---|---|---|---|
| **style** | `fontSize` `color` `padding` `radius` | 显示差一点 | ✅ 开放集合，未知键忽略 |
| **behavior** | `merge: append`、`virtualize` | **内容错**（如每次重连列表重复一遍） | ❌ 封闭枚举，未知键**整节点降级** |
| **structure** | `slot` `children` | 内容整块消失 | ❌ 封闭枚举 |

判据一句话：**这个字段改变的是「数据内容」还是「它的外观」？** 改内容 → 视为契约；只改外观 → 可自由加。

为什么 behavior 不能忽略：忽略后的结果在界面上「有内容、不崩、不报错」，只是数据悄悄变长，肉眼看不出来。**一律兜成「不支持」才是最坏的做法。**

#### 9.4 生成方式：不用 AI，改为模板填充

```
事件 → 查表拿模板 → 填数据 → 渲染
```

- **好处**：同类事件永远得到同一份骨架，样式不漂移；JSON 可审查、可 diff、可测试。第六节「AI 选不准控件」那一整套风险整体不成立。
- **代价**：同步责任从协议转移到**人**。dsh 电脑端新增事件后需人工补模板，且这是流程风险（没有编译错误、没有异常日志，只表现为「某类事件安静地走了兜底」）。
- **保留的判断**：「10 个原语拼 100+ 类别」仍然成立，但目的从「让 AI 选得准」变成「让人少写一份模板」。

#### 9.5 兜底：先判「该不该支持」，再决定说什么

| 情况 | 用户看到 | 是否告警 |
|---|---|---|
| 电脑端专属事件（`platform: pc`） | 「需在电脑端查看」+ 跳转锚点 | 否（仅计数） |
| 通用事件但客户端版本旧 | 「请升级客户端」 | 否（仅计数） |
| 通用事件但类型未知 | **原文卡（默认折叠、≤4KB）** + 标记异常 | **是** |
| 解析失败 | 错误卡（带原始字节长度） | **是** |

**核心约束：兜底不能成为 bug 的掩体。** 若把全部认不出的都统一显示「本地不支持」，线上所有真故障都会伪装成正常状态。前两行是产品行为，后两行是工程行为——**只有后两行需要上报和告警**。

另：「需在电脑端查看」必须带锚点（会话 / 任务 id，或可直接打开的 `dsh://` 引用）。没有锚点，这条提示的价值为零，用户看完还得自己找。

JSON 原文卡三条限制：截断到 4KB、默认折叠、单行横向滚动不撑开布局。

#### 9.6 对账与过滤

**能力对账（事前，能让问题根本不发生）**——协商粒度必须细到 **schema 版本**，不能只报形状名：

```
客户端：我支持 card@2, text@1, row@1
服务端：映射表记 diff_v2 需要 card@2 → 版本不够则不下发
```

只报「我认 card」，服务端会下发需要 `card@2` 的内容——**对账通过，实际仍降级**。这是对账机制永远补不平的缝：协商粒度天生比语义粗。

**遭遇对账（事后）**——真遇到不认识的类型时上报，四条硬约束：

1. **旁路**：不进渲染主路径，渲染完再异步处理
2. **可丢**：失败即丢，不重试、不阻塞、不弹提示
3. **去重键用 `(type, client_version)`**：只用 type 会让升级后的新问题被当成「已报过」
4. **只报类型 / 版本 / 计数，不报 payload**（payload 可能含用户输入内容）

**过滤必须留底**：可以丢数据，不能丢「丢了多少」这个事实。保留被过滤总数，否则出问题时无法判断是否被自己的过滤逻辑吃掉。过滤状态按 `(type, version)` 设上限（如 500 条），避免它自己变成内存泄漏源。

**附带收益**：五·六·五 的「白名单只增不删」是**没有数据时**的保守策略；有了对账数据后，可升级为「90 天零命中即可删」——从「不敢删」变成「有据可删」，这是防止协议无限膨胀的唯一出路。

#### 9.7 需要 dsh 电脑端配合的三件事

| # | 事项 | 为什么必须由对端做 |
|---|---|---|
| 1 | 事件带 `platform: pc \| any` 标记 | 客户端无法自行判断「不支持」是正确状态还是 bug |
| 2 | 事件带可跳转锚点（会话 / 任务 id） | 否则手机端的提示无法落到具体位置 |
| 3 | 新增事件时同步告知类型名 | 客户端靠人工同步模板，源头在对端 |

#### 9.8 检查项（草稿，两处数值待实测回填）

| # | 检查对象 | 获取方式 | 判定标准 | 执行时机 |
|---|---|---|---|---|
| C1 | 按 id 作排序键的代码 | `git grep` 正则搜 `sortBy { … .id }` | = 0 处 | 每次提交 |
| C2 | 新增一类的改动面 | 建真实新类别分支 → `git diff --stat` | = 0 个文件（只改服务端配置）；若需改代码，说明已超出配置表达力 | 每次新增 |
| C3 | 未知类型降级 | 投一条 `type="__fake__"` 事件 | 不崩 + 降级卡可见 + 计数 +1 | 改渲染器后 |
| C4 | 半截 JSON 分片 | `tool_call` 参数切 3 片依次投递 | 解析错误 = 0；streaming 期不渲染内容 | 改流式逻辑后 |
| C5 | 重连重放 | 同批事件投两遍且顺序打乱 | part 数正确 / 0 重复 / 0 丢失 | 改 reducer 后 |
| C6 | 事件表覆盖度 | dsh 版本 → 客户端事件表逐类核对 | **缺任一新类型 = 失败** | dsh 每次升级后 |
| C7 | 滚动稳定性 | 500 条对话快速上下滑 | 无位置回跳；jank 占比不劣于基线 | 发版前 |

**两条待回填（先记着，别当定稿）**：

- **C2 的「0」有前提**：类别映射入口必须唯一。若 `ComponentTypes` 与「component_type → 渲染器」映射表各存一份，「改一处」就是假目标，得先合并入口再定门槛。
- **C7 的基线尚未实测**：需先在 500 条对话上跑一次 Macrobenchmark 取当前 jank 占比，再定「不劣于基线」。**写死一个无依据的数字比空着更糟，会倒逼执行的人去凑数。**

#### 9.9 本节一句话

**兜底管「出事不出屏」，对账管「事不发生」，过滤管「别吵」。**

三者各管一段，缺任何一段都会退化成三种病：用户白屏、你不知情、数据被噪声淹掉。

## 六、AI 如何稳定生成 UI

### 6.1 反直觉的结论

**文档越长，AI 越不会用。** 现在是 110 行里塞 60 多个控件、每个一行，模型很容易漏、容易混（如 `alert` 与 `notice`）。

### 6.2 决定成败的三样东西

1. **Schema 比文档重要**：用 enum 约束，让模型从选项里选
   ```json
   {"type": {"enum": ["card","text","button","table","chart"]},
    "tone": {"enum": ["default","primary","danger","success"]}}
   ```
2. **每个控件一个最小示例**，一行示例顶十行说明
3. **报错要能直接改**：
   - ✗ `Invalid argument`
   - ✓ `新卡不支持 children 里的 type=html；可用：text/card/image/table`

### 6.3 真正的闭环

```
AI 生成 JSON → schema 校验 → 结构化报错 → AI 自我修正
```

有了这个闭环，文档可以很短；没有它，写一万字也拦不住模型写错。

### 6.4 文档拆分建议

- **速查卡（≤100 行）**：控件名 + 必填字段 + 一行示例 → 进系统提示词
- **全量规范**：按需检索
- **`control_lookup` 升级**：传控件名 → 返回该控件 schema 与示例，让 AI 用哪个查哪个

## 七·五、验收判据（v1.1 新增）

v1.0 每条都是「建议做 X」，但**没有一条写清做完怎么算成功**。没有判据，改造容易变成「改了一半、感觉好点了、然后停了」。每条挂一个可测指标：

| 改造项 | 验收判据（可测） | 怎么测 |
|---|---|---|
| 样式收敛 | 新增一个纯组合控件，需要改动的文件数从当前 **≥5**（`ComponentRegistry` + `ComponentTypes` + `ComponentTheme` + `CardShell` + 对应 CardView）降到 **1** | 拿 `steps` 演练一次，数 `git diff --stat` 涉及文件数 |
| 主题收敛 | debug 抛异常打开后，**7 个预设 × 深浅两档**全走一遍，崩溃数 **= 0** | 写一个遍历 Activity，或参数化 androidTest |
| 预览台 | 改一个控件样式，从「改代码→编译→装包→造消息」到「改 JSON→即时出图」，**闭环 < 30 秒** | 掐表 |
| 对话页 | 500 条长对话（含 WebView 卡片）滚动 jank 帧占比 **< 1%**；`notifyDataSetChanged` 调用 **= 0** | Macrobenchmark / `git grep` |
| 双轨收敛 | 已收敛控件的专用 CardView 引用 `git grep` **= 0**，且历史消息渲染回归全通过 | grep + 老数据回放 |
| Motion token | `setDuration(` 后直接跟数字字面量的调用 **= 0** | grep |
| 包体积 | 开 `minifyEnabled` + `shrinkResources` 后，APK 体积对比基线有明确下降，且全量功能回归通过 | 出包对比 |
| 无障碍 | 关键交互路径（发送/停止/展开/复制）`contentDescription` 覆盖 **= 100%** | 人工走查（当前全项目仅 24 处） |

**判据的附带价值**：它顺手定义了「什么时候可以停」——没有这一步，收敛永远做不完。
