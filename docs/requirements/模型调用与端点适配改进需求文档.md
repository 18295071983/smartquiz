## 一、核查方法（可复现）

1. **读配置**：`/data/user/0/com.oilquiz.app/shared_prefs/` 下 `online_models_config.xml`、`ai_config.xml`、`ai_service_prefs.xml`、`cap_probe_cache.xml`、`fc_probe_cache.xml`、`ctx_window_cache.xml`、`model_state_cache.xml`、`model_cold_start_prefs.xml`、`api_keys.xml`。

## 三、P0 需求（先做，收益最高）

### M1 端点 URL 规范化拼接（修 URL 拼接 Bug）

- **现象**：配置 `apiUrl = https://open.bigmodel.cn/api/paas/v4`（厂商官方正确地址），引擎按 OpenAI 习惯再追加 `/v1`，实际请求 `.../api/paas/v4/v1/chat/completions` → 404。
- **根因**：拼接前未判断 base_url 是否已含版本路径段。
- **改进要求**：
  1. 新增统一函数 `buildEndpoint(baseUrl, path)`：去尾部斜杠 → 识别是否已含 `/v1`、`/api/xxx/vN` 等版本段 → 仅在**未含**时补默认版本 → 拼接路径。
  2. chat/completions、models、usage、audio、embeddings 等**所有**端点复用同一函数。
  3. 拼接结果写入日志（DEBUG 级，便于诊断）。
- **验收标准**：
  - `https://open.bigmodel.cn/api/paas/v4` → `/api/paas/v4/chat/completions`（不重复）✅
  - `https://api.deepseek.com` → `/chat/completions` 或 `/v1/chat/completions` ✅
  - `https://api.openai.com/v1` → `/v1/chat/completions`（不重复）✅
  - 日志中不再出现任何 `.../vN/v1/...` 形态路径。

### M2/M3 能力探测：先修探测请求，再改失败策略

- **现象**：探测请求本身非法——`function 'ping_probe'` 的 schema 为 `type: null`，被服务端 400 拒绝；随后日志打出 `defaulting to supported (avoid degrading)`，即**探测失败一律当作"支持"**。
- **危害**：探测等于白跑（每次对话白付一个 400 请求），且对不支持 FC 的模型会误判为支持，问题推迟到真实调用时才爆。
- **改进要求**：
  1. 修正 `ping_probe` 的 JSON Schema：`{"type":"object","properties":{},"required":[]}`，工具名/结构符合 OpenAI function 规范。
  2. 探测结果改为**三态**：`supported / unsupported / unknown`；`unknown` 不得直接等同于 supported。
  3. 探测结果**按「厂商 + 模型」缓存并带 TTL**（如 7 天），避免每次会话重复探测。
  4. 探测失败区分原因：网络不可达（可重试）≠ 服务端 400（说明请求非法，应告警并停止探测）。
- **验收标准**：日志中 `Probe HTTP 400` 归零；`defaulting to supported` 归零；探测请求每个模型每次会话 ≤ 1 次。

### M4/M5 语音链路端点补齐（语音输入/合成是当前最大功能缺口）

- **现象**：
  - 语音识别：`isAvailable: false (no voice provider endpoint found)` 反复出现（单日 42+ 次），本地已有 239MB 中文 ASR 模型文件却未被纳入可用链路；另有 `音频文件不包含音轨` 报错 13 次。
  - 语音合成：`在线TTS失败 ... HTTP 404` **2677 次**；音色列表按 `/audio/speech/voices` → `/audio/voices` 顺序盲试三次，全部 404 后回退预设。
- **根因**：语音能力没有独立的"服务商适配层"，直接拿 LLM 的 base_url 去猜 audio 路径。
- **改进要求**：
  1. 语音模块独立配置 `voice provider`（地址、Key、协议），与 LLM 配置解耦，不复用 LLM 的 base_url。
  2. 音色列表地址按厂商**显式配置**，取消"路径盲试"逻辑；盲试仅作兜底且最多 1 次。
  3. 本地 ASR 模型（`files/asr_model.int8.onnx`）纳入可用性判定：本地可用时 `isAvailable` 应为 true。
  4. 录音文件增加音轨校验与友好提示（"没录到声音，请检查麦克风"）。
- **验收标准**：语音输入可用（本地或在线任一）；TTS 404 次数归零；音色列表一次请求命中；不再出现 `no voice provider endpoint found`。

### M6/M7 思维链（reasoning）协议适配

- **现象**：
  - `StreamV2 API failed: HTTP 400: {"message":"The `reasoning_content` in the thinking mode must be passed back to the API."}`
  - 同时大量 `content为空，回退使用reasoning_content作为回复`：把思维链内容当正文展示。
- **根因**：未按推理模型协议处理 `reasoning_content`（多轮需回传；且不应作为正文输出）。
- **改进要求**：
  1. 会话上下文中保留并回传 `reasoning_content`（厂商要求时），或按厂商开关关闭 thinking 模式。
  2. `content` 与 `reasoning_content` 严格分离：思维链仅用于"思考过程"折叠展示，不得填充正文。
  3. 按厂商/模型区分协议差异（是否需回传、字段名是否不同）。
- **验收标准**：不再出现该 400；`回退使用reasoning_content作为回复` 日志归零；思考过程与正文各就各位。

### M8/M9 网络鲁棒性（端口/私有化部署的前置条件）

- **现象（实测复现）**：
  - 明文 `http://` 请求会导致 Python 执行环境**整体猝死**，`print("start")` 之后进程直接退出，`try/except` 完全兜不住（连 `end` 都打不出来）。
  - 域名不可达（DNS 解析卡住）时，`socket` 超时不生效，单次调用被拖到 **30 秒工具硬超时**才返回失败。
- **危害**：局域网/内网私有化部署（`http://192.168.x.x:端口`、Ollama `127.0.0.1:11434` 等）完全不可用；一个卡住的请求会白等 30 秒并拖垮整轮对话。
- **改进要求**：
  1. 网络请求统一封装：连接超时 + 读取超时 + **总超时**三重限制（建议连接 5s、总 30s 可配）。
  2. DNS 解析放入可超时路径（或使用带超时的解析），避免卡死在解析阶段。
  3. **支持明文 http 且不得崩溃**：按需放开 cleartext 策略（可加白名单），异常必须能捕获并返回可读错误。
  4. 失败重试策略明确：网络类错误可重试（指数退避，最多 2 次）；HTTP 4xx 不重试。
  5. 用户可读报错：区分"地址不通 / 认证失败 / 路径不存在 / 模型不存在 / 余额不足"，并给出修复建议。
- **验收标准**：`http://` 地址可正常请求或返回明确错误（不崩溃）；不可达域名 5 秒内返回失败；单次调用不会零散占用 30 秒以上。

## 四、P1 需求（体验加分项）

### M10 URL 规范化与缓存键统一
`ctx_window_cache.xml`、`cap_probe_cache.xml` 中同一地址因尾斜杠产生两份记录（`.../api/paas/v4` 与 `.../api/paas/v4/`）。
**要求**：所有缓存键基于规范化 URL（小写、去尾斜杠、统一协议）；上线时做一次键迁移/清理。

### M11 模型元数据单一数据源
现状：`cachedModelsJson` 中 `contextLength` 全部硬编码 `1000000` 且 `contextLengthFromApi:false`；而 `ctx_window_cache` 里是 1048576 / 202752 / 131072 等真实值，两套口径并存。
**要求**：
1. 窗口长度优先级：接口返回 > 内置厂商表 > 保守默认值；**禁止硬编码 1000000**。
2. 单一数据源，UI 与引擎读同一份。
3. 内置厂商/模型表支持**按厂商名索引**（当前只能按模型名搜，实测搜 `openai` 无结果、搜 `gpt` 才有）。

### M12 密钥与日志安全
- `online_models_config.xml` 中 API Key **明文**存储；
- AI 日志完整记录了携带 Key 的请求体/代码参数（可被任意读日志的功能读到）。
**要求**：Key 使用 Keystore/加密存储；日志统一脱敏（`sk-****`）；禁止把 Key 写入对话历史与工具参数日志。

### M13/M14 初始化时序与意图识别
`Agent模式需要AI服务已初始化，当前AI服务未就绪`（125 次）说明存在竞态；`Unknown intent or no task type`（110 次）说明意图识别有明确失败面。
**要求**：初始化完成前的用户请求应排队或给出明确状态提示；意图识别失败要有兜底（转通用对话而非报错）。

### M15 资源占用
`local_agent_enabled=false` 时本地模型仍被加载（4B 平均加载 40s、最多 57s、已加载 8 次/2B 已加载 84 次），并伴随 `内存使用警告: 92.2%`、`resident=1.9GB, size=20.3GB`、内存池被迫 2048MB→1515MB。
**要求**：本地模型按需懒加载 + 空闲自动卸载；关闭本地 Agent 时不应加载模型；给出内存使用可视化。

## 五、P2 增强

1. **多端点故障转移**：同一厂商配置主/备地址，主不可达自动切换。
2. **厂商模板一键配置**：内置常见厂商（DeepSeek、智谱、通义、Kimi、MiniMax、豆包、OpenAI、Anthropic、Gemini、Ollama）的 base_url/协议/认证方式模板，用户只填 Key。
3. **协议抽象**：模型配置新增 `protocol` 字段（`openai | anthropic | gemini | ollama`），支持不同的认证头（`Authorization: Bearer` / `x-api-key` / query `?key=`）与请求体格式。当前配置只有 `apiUrl/apiKey/apiSecret/appId`，无法表达这些差异。
4. **成本用量统计**：按模型/厂商维度统计 token 与费用（日志中已有 usage 数据可复用）。
5. **流式乱码治理**：`流式输出检测为乱码，已清理非法字符`（70 次）——应从流式解析层修复（分片边界/编码），而非事后清洗。
6. **连通性自检按钮**：模型配置页加"测试连接"，一键验证地址/Key/模型名/协议（本次 Bug 若有一个测试按钮，用户当场就能发现）。

## 增补（2026-09-11）：GLM-5.3 模型切换适配需求（建议文档版本升至 v1.1）

> **背景**：2026-09-11 激活模型由 DeepSeek 切换为 **GLM-5.3**（智谱 Z.ai）。本节为本次切换新增的适配需求，与上文 M1、M6/M7、M10、M11 直接相关，后端可据本节自行更新模型配置表。

### 新增需求 M16：模型元数据表接入 GLM-5.3

- **查证数据**（官方/权威来源，查证日期 2026-09-11）：
  - 模型：GLM-5.3，大规模推理模型，主打编程与长程智能体任务；2026-08-14 发布，2026-08-29 开源权重
  - 上下文窗口：**1,000,000 tokens（原生 1M）**；来源：vLLM 官方 recipes `https://recipes.vllm.ai/zai-org/GLM-5.3`（"native 1M-token window"），ArtificialAnalysis 对比页同口径 1000k
  - 服务商：智谱 Z.ai；端点：`https://open.bigmodel.cn/api/paas/v4`
- **需求条目**：
  1. 模型配置表新增条目：`{"match":"glm-5.3","contextWindow":1000000,"provider":"智谱Z.ai","source":"https://recipes.vllm.ai/zai-org/GLM-5.3","date":"2026-09-11"}`
  2. 清理同端点历史缓存 key（`/api/paas/v4` 与 `/api/paas/v4/` 两份重复，见 M10），避免新旧窗口值混用。
  3. `contextLength` 与 API 探测值统一口径（关联 M11）：以本表 1M 为准，`contextLengthFromApi` 探测成功后回写，不再硬编码多套数值（1048576/202752/131072 并存问题一并收敛）。
  4. 若聚合商/网关对该端点限窗，用 `apiUrl` 字段单列一条限窗值，不影响全局条目。
- **验收标准**：切换 GLM-5.3 后上下文截断按 1M 计算；ctx_window_cache 中不再出现同一端点多份 key；元数据只有一套口径。
