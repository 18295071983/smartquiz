# UI 组件系统改进需求文档

| 项目 | 说明 |
| --- | --- |
| 文档版本 | v1.0 |
| 日期 | 2026年9月11日 |
| 提出方 | AI 助手（基于实际使用中的痛点反馈整理） |
| 适用范围 | App「AI 对话」模块的 UI 组件系统（内置卡片 / 原生交互组件 / layout 动态布局框架） |

---

## 一、背景

AI 助手在「AI 对话」功能中承担完整 Agent 职责，需高频调用 UI 组件系统，将结构化信息（列表、表格、图表、指标、表单等）以卡片或动态布局形式呈现给用户，并与用户完成交互（选择、输入、确认等）。

在实际使用过程中，暴露出若干影响**开发效率**与**交付确定性**的问题。本文档旨在系统梳理痛点，给出可落地的改进方案与优先级建议，供研发 / 外包团队评估实施。

## 二、现状概述

当前 UI 组件系统主要由三套能力构成：

1. **内置卡片**：props 驱动，如 chart / table_card / info_card 等，开箱即用。
2. **原生交互组件**：dialog / input / choice 等，需 get_result 取回用户结果。
3. **layout 动态布局框架**：以 JSON 控件树描述界面，现场渲染，灵活度最高。

三套能力功能强、覆盖广，但在「开发体验」与「交付确定性」上存在明显短板，核心痛点集中在：**缺乏预览、缺乏校验、命名不统一、异步回传体验差、选型边界模糊**。

## 三、改进需求清单

### P0 高优先级（投入小、收益大，建议优先实施）

#### P0-1 布局实时预览 + 创建前校验（dry-run）
- **现状问题**：layout 需手写 JSON 控件树，创建前无法预览渲染效果，只能「建出来才知道长啥样」，试错成本高，出错只能重建。
- **改进方案**：
  - create / layout_editor 支持 dry-run 预校验模式，返回布局是否合法而不实际渲染；
  - layout_editor 提供所见即所得实时预览渲染；
  - 校验覆盖：控件 type 合法性、必填字段、key 缺失、嵌套结构错误、options / 数值越界等。
- **验收标准**：提交 layout 前即可看到渲染预览；非法布局返回明确错误且不产生脏组件。

#### P0-2 参数前置校验与精确定位
- **现状问题**：组件字段多且不规范，字段名记混后只能「现查现试」；出错时错误信息不指明具体节点，定位困难。
- **改进方案**：
  - 创建前统一执行 schema 校验；
  - 错误信息携带节点路径（如 `root.children[2].rows`）与字段名；
  - 常见错误给出修复建议（缺 key / 非法 type / 类型不匹配）。
- **验收标准**：非法参数在创建前即被拦截，报错精确到节点与字段。

#### P0-3 组件字段命名规范化
- **现状问题**：同类语义字段命名不统一，例如 alert 的样式字段为 `alert_type` / `variant`，而其他控件多用 `type`，极易混淆。
- **改进方案**：
  - 制定并统一全组件字段命名规范：`type`（结构类型）/ `variant`（样式变体）/ `style`（自定义样式）；
  - 对历史不一致字段提供别名兼容，避免破坏存量调用。
- **验收标准**：命名规范文档落地；同类字段跨组件命名一致。

### P1 中优先级

#### P1-1 异步回传体验优化
- **现状问题**：get_result 为阻塞式等待，用户未操作时长期挂起，超时后组件状态不明，难以续取。
- **改进方案**：支持事件回调 / 续取机制；超时后保留组件状态，可再次取回结果；提供「用户未响应」的明确状态。
- **验收标准**：超时后可续取，组件状态可查询、不丢失。

#### P1-2 三条能力路径边界厘清
- **现状问题**：内置卡片 / 原生组件 / layout 三条路径边界模糊，同一界面存在多种实现方式，选型纠结，偶有功能重叠。
- **改进方案**：提供选型指引或统一入口，可根据需求自动推荐 / 判定实现路径。
- **验收标准**：有明确的选型决策树；典型场景有单一推荐实现。

#### P1-3 样式控制能力增强
- **现状问题**：间距、圆角、配色、字号等精细样式难以调整，设计表现力受限。
- **改进方案**：layout 支持统一 `style` 对象（padding / margin / radius / background / border / font / color 等）。
- **验收标准**：常用样式可通过 style 对象配置并生效。

#### P1-4 组件生命周期与 id 管理
- **现状问题**：组件创建后需维护 component_id，数量增多后更新 / 关闭易误操作。
- **改进方案**：支持命名组件（key）；提供组件列表查询与批量更新 / 关闭能力。
- **验收标准**：可按名称引用组件；支持批量操作。

### P2 低优先级（体验优化）

#### P2-1 响应式适配
- **现状问题**：宽高单位与布局在不同屏幕下表现不一致，小屏易挤压。
- **改进方案**：统一响应式单位与断点规范。
- **验收标准**：主流屏幕尺寸下布局正常。

#### P2-2 错误定位与调试能力
- **现状问题**：报错不指明节点，调试困难。
- **改进方案**：错误信息带节点路径；提供调试视图。
- **验收标准**：可快速定位出错节点。

#### P2-3 交互反馈
- **现状问题**：按钮点击无 loading，提交无成功 / 失败反馈。
- **改进方案**：内置 loading 态与成功 / 失败态。
- **验收标准**：交互有即时视觉反馈。

## 四、优先级与排期建议

| 阶段 | 内容 | 预期收益 |
| --- | --- | --- |
| 第一阶段 | P0-1 / P0-2 / P0-3 | 解决约 80% 的「现查现试」，显著提升交付确定性 |
| 第二阶段 | P1-1 ~ P1-4 | 提升交互体验与开发效率 |
| 第三阶段 | P2-1 ~ P2-3 | 完善细节与健壮性 |

## 五、验收标准汇总

1. layout 支持创建前预览与 dry-run 校验，非法布局被拦截；
2. 参数错误报错精确到节点路径与字段名；
3. 全组件字段命名规范统一，历史字段有别名兼容；
4. get_result 超时后可续取，状态不丢失；
5. 三条能力路径有明确选型指引；
6. 常用样式可通过 style 对象配置；
7. 组件支持命名引用与批量操作；
8. 主流屏幕下布局正常；
9. 错误可快速定位到节点；
10. 交互具备 loading / 成功 / 失败反馈。

## 六、范围与备注

- 本文档基于 AI 助手实际使用反馈整理，侧重「开发体验与交付确定性」，不代表全部功能诉求。
- 字段命名统一（P0-3）需评估对存量调用的兼容影响。
- 具体技术实现方案（接口设计、数据结构等）由研发团队评估确定。
- 建议按 P0 → P1 → P2 分阶段实施，优先验证 P0 的收益。
