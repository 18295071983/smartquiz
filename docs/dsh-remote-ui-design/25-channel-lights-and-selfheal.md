# 25 · 多通道状态灯与「对码」自愈（方案 · 待审批）

> 用户口径：通道一直是绿灯太粗；每个端口要**各自的灯**并做检测；全正常时**呼吸闪烁**，
> 故障切到对应灯；**主通道正常、支路故障**时，手机把状态回报服务端，由服务端下发修复指令。

---

## 1. 现状

- 顶栏只有一个状态点：`ServiceStatusManager` 的 `lastDotColorRes`（绿=在线 / 黄=要人处理 / 灰=断）；
  它只看"主连接是否在线"，**不看每条通道各自的死活**。
- 通道已经有 5 条：`/ws/events`、`/ws/ui`、`/ws/alert`、`/ws/file`、`/ws/ctl`；
  插件 `/status` 已暴露 `ws_channels`（每个端点在线连接数）。
- 每条通道已有保活：服务端 15s `ws.ping()`、客户端 20s OkHttp ping、`hello` 握手。
  **但客户端没有逐通道的健康判定，也没有聚合展示。**

---

## 2. 灯模型（每通道一盏）

| 通道 | 灯位 | 颜色语义 |
|---|---|---|
| 主连接（devices/`/status` 可达） | 主灯 | 绿=正常 · 黄=要人处理 · 灰=断 |
| `events` | 事件灯 | 绿=有 ready 且 30s 内有帧 · 黄=重连中 · 红=握手失败 · 灰=未启用 |
| `ui` | 指令灯 | 同上 |
| `alert` | 告警灯 | 同上（**它红=最严重**，审批推不到） |
| `file` | 文件灯 | 灰=未使用（默认）· 绿=传输中 · 红=上次传输失败 |
| `ctl` | 控制灯 | 灰=未使用 · 绿=正常 |

**呼吸**：仅当**所有已启用通道都是绿**时，主灯做呼吸动画（alpha 0.4→1.0，周期 2200ms）；
任一通道非绿 → 呼吸停止，对应灯常亮告警色。

**聚合灯**（顶栏那个）：取"最差"状态——有红显示红，有黄显示黄，全绿则绿+呼吸。

---

## 3. 健康判定（客户端，纯本地）

每条通道维护一个 `ChannelHealth`：

| 字段 | 更新时机 | 判定 |
|---|---|---|
| `state` | 握手/断开/错误 | `connecting / ok / degraded / dead / off` |
| `lastFrameAt` | 收到任何帧（含 pong） | 超过 **35s** 无帧 → `degraded`；超过 **70s** → `dead` |
| `lastPongRtt` | `ping`→`pong` | 大于 3s 记 `degraded` |
| `failCount` | 连接失败 | ≥3 次 → `dead` |

`file` / `ctl` 默认 `off`（不连就不算故障）。

---

## 4. 对码（手机回报 → 服务端下发修复）

复用 `/ws/ctl`（控制面）。**三条硬约束**：

1. **服务端不忙等**：服务端没有针对每条连接的定时探测、没有轮询循环、不主动催；
   它只在收到 `diag` 帧时醒来算一次、回一条 `repair` 就结束。
2. **客户端发起**：谁有病谁说话——手机本地已经知道每条通道的死活（35s/70s 无帧、3 次失败），
   状态一变就上报；不靠服务端来问。
3. **不双方确认**：`repair` 是**单向指令**，手机收到就执行，不回 ack、不等确认；
   执行结果自然体现在下一次 `diag` 里（状态变绿或仍红），服务端不需要"确认收到"。

**手机 → 服务端**（状态变化时发；稳态每 30s 发一次保活，不发也行）

```json
{ "type": "diag", "session_id": "...", "channels": [
  {"name":"events","state":"ok","rtt_ms":12,"silent_ms":900},
  {"name":"ui","state":"dead","rtt_ms":0,"silent_ms":71000},
  {"name":"alert","state":"ok","rtt_ms":9,"silent_ms":1200}
]}
```

**服务端 → 手机**（只在有建议时回；无事可不回）

```json
{ "type": "repair", "actions": [
  {"channel":"ui","action":"reconnect"},
  {"channel":"events","action":"resync","since":6812}
] }
```

**修复动作白名单（只有 5 个）**

| 动作 | 客户端做什么 |
|---|---|
| `reconnect` | 关掉该通道重连（含关闭重复 socket） |
| `resync` | 用 `/ws/events` 的 `pull` 从 `since` 补齐 |
| `drop_duplicates` | 关掉同通道里除最新一条外的连接（治 socket 泄漏） |
| `refresh_snapshot` | 请求一份 snapshot 重建时间线 |
| `none` | 不用处理 |

安全边界：服务端只能建议，客户端校验白名单后执行；未知动作丢弃并记日志。

### 4.1 网络波动：全自动，不打扰用户

| 场景 | 处理 |
|---|---|
| 单条通道掉 | 客户端自己按退避重连（1s→30s 抖动），**不弹窗、不问用户** |
| 主连接掉 | 顶栏聚合灯变灰，客户端继续重连；恢复后自动回填 |
| 重连后缺口 | 用 `since` 游标 `pull` 补齐（幂等重放，不重复落屏） |
| 修不好 | 累计 3 次失败才把状态显示为红；仍不弹对话框，只在甲板留一行 |

一句话：**能自己好的绝不问用户，必须让用户知道的才进甲板/通知**。

## 5. 展示位置（2026-11-14 修订：不做"一排灯"）

一排五六个圆点既看不清、又认不出谁是谁，还得数第几个——不合适。改成：

| 位置 | 形态 | 理由 |
|---|---|---|
| 顶栏 | **只留一盏聚合灯**（全绿呼吸；否则取最差颜色常亮） | 一眼、不占地 |
| 甲板 | **一行文字**：`通道 5/5 正常` / `告警通道异常 ›` | 文字能说出"哪里坏"，比灯有用 |
| 远程连接页 | **竖排列表**：每行 `● 事件通道 · 12ms · 正常` | 竖排行距大、有标签，比横排圆点好读 |
| 诊断页 | **一条分段色带 + 表格** | 色带是一根横条分成 5 段（谁坏哪段变色），配下方表格给名称/RTT/静默时长；仍是一个视觉元素 |

两条原则：

1. **灯只在异常时出现**：全绿时屏幕上不显示任何通道灯，顶栏那盏呼吸的聚合灯已经表达"都正常"；
   非绿（黄/红）才亮出对应通道的灯或段。
2. **顶栏永不增加灯的数量**：聚合灯永远只有一盏，明细一律去诊断页。

## 6. 分阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| **L1** | 插件 `/status` 增每通道 `last_frame_at` / `connects` / `errors`；`ws_channels` 保留 | curl 能看到 5 条通道的统计 |
| **L2** | 手机 `ChannelHealth` + `ChannelLights` 渲染 + 聚合灯 + 呼吸动画 | 真机：拔一条通道（关插件再开）→ 对应灯变红，其它不变 |
| **L3** | 对码协议：`diag` 上报 + `repair` 下发 + 5 个动作 | 造一个重复 ui socket → 服务端下发 `drop_duplicates` → 手机上多余的连接被关 |
| **L4** | 甲板诊断行 + 诊断页 | 真机：甲板显示「通道 5/5」，点开看明细 |

---

## 7. 风险

| 风险 | 处置 |
|---|---|
| 灯太多反而看不懂 | 顶栏只放聚合灯；明细在诊断页；甲板一行摘要 |
| 误判（弱网抖动频繁变红） | 判定阈值 35s/70s + 连续 3 次失败才算 `dead`；`degraded` 用黄色不报警 |
| 呼吸动画耗电 | 只在页面可见时跑；熄屏/后台停 |
| 服务端下发修复被滥用 | 白名单 5 个动作 + 客户端校验 + 每 60s 最多执行 3 次 |
