# 25 · 通道健康与自愈（方案 v2 · 已按评审调整）

> 用户口径：通道状态一直是绿灯太粗，要能反映各端口状态；故障时手机回报、服务端下发修复；
> 服务端不忙等、不双方确认、网络波动自动修复。
> **v2 修订**（2026-11-14）：砍掉"一排灯"，删除危险的 `drop_duplicates`，加熔断与 dry-run，
> 并把"每通道单 socket"提升为客户端不变量（今天 socket 泄漏的根因治理）。

---

## 0. 先说结论：三件事按这个顺序做

| 顺序 | 做什么 | 为什么排前面 |
|---|---|---|
| **H1** | **每通道单 socket 不变量**（客户端唯一入口 + 单测） | 今天 UI 通道堆到 3 条的根因；不从根上消灭，自愈协议只会反复收拾 |
| **H2** | **聚合灯 + 断因记录**（信息量最大、风险最低） | 单通道异常才亮灯；断因比颜色有用 |
| **H3** | **对码自愈（先 dry-run 一周）** | 服务端只算"我会建议什么"并写进诊断页，**不执行**；观察一周再放开 |

---

## 1. 现状

- 顶栏只有一盏 `ServiceStatusManager` 的状态点，只看主连接，**不看各通道死活**；
- 通道已有 5 条：`/ws/events`、`/ws/ui`、`/ws/alert`、`/ws/file`、`/ws/ctl`；
- 插件 `/status` 已暴露 `ws_channels`（各端点在线数）与 `ws_stats`（`connects/frames/last_frame_at/closes`）；
- 已有保活：服务端 15s `ws.ping()`、客户端 20s OkHttp ping、`hello` 握手；
- 客户端**没有**逐通道健康判定，也没有断因记录。

---

## 2. 灯：默认只有一盏聚合灯

真实故障形态只有四种：手机断网/切网（**全断**）、插件重启（全断重连）、单通道僵尸（**单条异常**）、
隧道劣化（一起变慢）。前两种占绝大多数，所以：

| 位置 | 形态 |
|---|---|
| 顶栏 | **唯一一盏聚合灯**：正常=绿（静态）/ 降级=黄 / 故障=红 |
| 顶栏（异常时） | 单通道异常 → 聚合灯旁多一行小字：`指令通道异常 ›`（点开诊断页） |
| 甲板 | 一行文字：`通道 5/5 正常` / `告警通道异常 ›` |
| 诊断页 | 表格（通道 / 状态 / RTT / 静默时长 / **最近断因**），异常行前置 |

**三态，不要四态**：正常（绿）/ 降级（黄）/ 故障（红）。未启用的通道（`file`、`ctl` 没连）**不显示**，
不占位、不画灰点。

**呼吸**：只在**连接建立或恢复后的 2 秒**呼吸一次（"好了"的反馈），之后静止。常驻呼吸是持续耗注意力。

---

## 3. 健康判定（客户端本地，不依赖服务端）

每通道维护 `ChannelHealth{state, lastFrameAt, lastRttMs, failCount, lastCloseReason}`：

| 判定 | 阈值 |
|---|---|
| 降级（黄） | 35s 无帧，或 RTT > 3s，或重连中 |
| 故障（红） | 70s 无帧，或连续 3 次连接失败，或握手 401/1008 |
| 正常（绿） | 其余 |

**断因记录**（H2 的核心）：每次断开记 `{at, reason, code, reconnectCount}`，诊断页展示最近 5 条。
原因分四类：`超时无帧` / `服务端关闭(code)` / `握手失败(401/1008)` / `本机关闭`。

---

## 4. 对码（客户端发起 → 服务端建议）

三条硬约束（用户要求）：

1. **服务端不忙等**：无逐连接定时探测、无轮询循环；只在收到 `diag` 时算一次、回一条 `repair` 就结束。
2. **客户端发起**：谁有病谁说话——状态一变就上报；稳态不额外上报。
3. **不双方确认**：`repair` 是单向指令，收到即执行，不回 ack；结果体现在**下一次 `diag`**。

### 4.1 协议

手机 → `/ws/ctl`：

```json
{ "type":"diag", "session_id":"…", "channels":[
  {"name":"events","state":"ok","rtt_ms":12,"silent_ms":900,"last_close":null},
  {"name":"ui","state":"dead","rtt_ms":0,"silent_ms":71000,"last_close":"timeout"}
]}
```

服务端 → 手机（**只在有建议时回**）：

```json
{ "type":"repair", "actions":[ {"channel":"ui","action":"reconnect"} ] }
```

**DIY 动作白名单（4 个，已删 `drop_duplicates`）**

| 动作 | 客户端做什么 |
|---|---|
| `reconnect` | 关掉该通道重连（幂等；若已有一条健康 socket 则不动） |
| `resync` | 用 `pull` 从 `since` 补齐 |
| `refresh_snapshot` | 请求 snapshot 重建时间线 |
| `none` | 不用处理 |

> **`drop_duplicates` 已删除**：它是在给客户端 bug 打补丁。正确做法是 H1 的
> "每通道单 socket" 不变量 —— 客户端持有一个 `Map<channel, WebSocket>`，
> 开新的前**必然**关闭旧的，并由单测断言"同通道永不并存两条"。

### 4.2 上报节流

- 状态变化**去抖 1.5s** 再发；
- 每分钟最多 **6 次** `diag`；超限丢弃（下一次状态变化自然会带最新状态）。

### 4.3 熔断（防修复风暴）

| 规则 | 值 |
|---|---|
| 同一通道修复频率 | **5 分钟内最多 2 次** |
| 连续无效 | 连续 3 次修复后该通道仍非绿 → **停止自动修复**，诊断页留「自动修复失败」 |
| 服务端重试 | **永不重试**，一次建议一次机会 |
| 全停条件 | 一条通道被熔断后，其余通道各自独立计数（互不牵连） |

### 4.4 dry-run（H3 第一周）

服务端照常算建议，但**只写进 `/status.repair_suggestions` 与诊断页**，`repair` 帧不发。
一周后观察建议是否准确（"建议 reconnect 之后真的好了吗"），再放开执行。

---

## 5. 网络波动：全自动，不打扰用户

| 场景 | 处理 |
|---|---|
| 单通道掉 | 客户端退避重连（1s→30s，抖动）；**不弹窗、不问用户** |
| 主连接掉 | 聚合灯灰/红，继续重连；恢复后自动回填 |
| 重连后缺口 | `since` 游标 `pull` 补齐（幂等重放，不重复落屏） |
| 修不好 | 3 次失败才显示红；仍不弹框，只在甲板留一行 |

一句话：**能自己好的绝不问用户，必须让用户知道的才进甲板/通知。**

---

## 6. 分阶段与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| **H1** | `RemoteChannel` 收敛为每通道单 socket（`Map<channel, WebSocket>`，开新先关旧） | 单测：连续 5 次重连后，`Map` 每通道仅 1 条；真机 `/status.ws_channels` 稳定 `{events:1, ui:1}` |
| **H2** | `ChannelHealth` + 聚合灯（三态）+ 断因记录 + 甲板一行 + 诊断页表格 | 真机：插件重启 → 聚合灯红→绿（恢复时呼吸 2s）；诊断页能看到最近断因 |
| **H3a** | `diag` 上报 + 服务端建议计算 + **dry-run** 展示 | 真机造一个异常 → 诊断页出现"建议：reconnect"，但**未执行** |
| **H3b** | 放开执行 + 熔断 | 真机：异常被自动修好；连续 3 次无效后停止并提示 |

---

## 7. 风险

| 风险 | 处置 |
|---|---|
| 自愈把客户端搞成重连风暴 | 熔断（4.3）+ dry-run 一周（4.4）+ 服务端不重试 |
| 灯太多看不懂 | 只有聚合灯；单通道只在异常时出现一行小字 |
| 呼吸耗电 | 只呼吸 2 秒；后台/熄屏不跑 |
| 误判（弱网抖动） | 35s/70s 阈值 + 3 次失败才红 + diag 去抖 1.5s |
| 服务端瞎建议 | 建议必须带依据（`silent_ms` / `last_close`），诊断页可对照 |
