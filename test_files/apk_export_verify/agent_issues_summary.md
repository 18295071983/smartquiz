# APK 导出器（export_apk）测试问题汇总

> 测试环境：小米17 / Android 16 / HyperOS 3
> 测试时间：2026-09-13
> 测试方式：真机构建导出 + 逐字节拆包验证 + 真机安装
> 总体结论：**核心功能可用，但有 1 个致命缺陷导致导出的包在 Android 11+ 全部装不上**

---

## 一、🔴 P0-1 「安装报 -124 / 提示不兼容」—— resources.arsc 未 4 字节对齐

### 现象
真机安装导出包，系统提示「**不兼容**」+ 错误码 **-124**（中文提示有严重误导性，让人误以为是机型/CPU 不匹配）。

### 真实含义（Android PackageManager 原文）
```
-124: Failed parse during installPackageLI:
Targeting R+ (version 30 and above) requires the resources.arsc of installed APKs
to be stored uncompressed and aligned on a 4-byte boundary
```

### 根因
壳模板 `targetSdkVersion = 34`（≥30），Android 11+ 强制要求 `resources.arsc`：
1. 必须 **未压缩（STORED）**
2. 数据起始偏移必须是 **4 的整数倍**

导出器只做对了第 1 条。实测：

| 检查项 | 实测值 | 判定 |
|---|---|---|
| arsc 压缩方式 | STORED | ✅ |
| arsc 数据偏移 | 2278531 | — |
| `偏移 % 4` | **3** | ❌ **不满足** |

**差 3 个字节，整包装不上。**

### 影响面
**100% 必现**，不是概率问题。targetSdk 固定 34 → 所有导出包在 **Android 11 及以上全部机型**都装不上。

### 修复
打包阶段对 `resources.arsc` 做 4 字节对齐（用 extra field padding，ID `0xD935`）：

```python
ALIGN_ID = 0xD935   # Android zipalign 官方 extra field ID

if name == "resources.arsc":
    zi.compress_type = zipfile.ZIP_STORED          # ① 不压缩
    cur = zout.fp.tell()
    A = cur + 30 + len(name.encode('utf-8')) + 4
    pad = (4 - A % 4) % 4                          # ② 补齐到 4 字节边界
    zi.extra = struct.pack('<HH', ALIGN_ID, pad) + b'\x00' * pad
```

或用标准工具：`zipalign -f -p 4 in.apk out.apk`

### ⚠️ 顺序铁律
```
打包（arsc 已对齐） → apksigner 签名（v1+v2+v3）
```
**绝不能反过来** —— 对齐会重排 ZIP 字节流，签名后再改会让 v2/v3 签名直接失效，照样装不上（targetSdk≥30 强制要求 v2+ 签名）。

### 建议加固
打包完成后、签名之前，加一句断言：`assert arsc_offset % 4 == 0`，不满足直接报错，避免带病出厂。

### 验证结果（已实测）
| 检查项 | 修复前 | 修复后 |
|---|---|---|
| arsc 压缩方式 | STORED | STORED |
| arsc 数据偏移 | 2278531 | 2283904 |
| `偏移 % 4` | 3 ❌ | **0 ✅** |
| 文件体积 | 2360935 B | 2359385 B |
| v1 签名摘要 | — | 未破坏 ✅ |

## 二、🔴 P0-2 并发导出会抢占同一个临时目录

### 现象
**同时发起 2 个导出，必挂 1 个**，报错「**无法创建临时目录**」。稳定复现两次。单独串行执行则全部成功。

### 根因
所有导出任务共用同一个固定临时目录，并发时后到者创建失败。

### 影响面
批量导出、用户连点、多任务并行场景直接不可用。报错信息也会误导为"磁盘/权限问题"。

### 修复建议
- 临时目录加唯一后缀：`tmp_export_<uuid4/时间戳+pid>`
- 或对导出流程加全局互斥锁（串行化，简单但会降低并发）
- 退出时确保清理，避免残留

### 佐证
同一批参数串行重试 100% 成功；仅并发时复现 → 确认是资源竞争，非参数问题。

## 三、🔴 P0-3 包名与签名写死，所有导出应用互相覆盖

### 现象
逐包比对 14 个导出包，**包名完全一致**：`com.cjhtmldemo.scedzxdz`，且使用同一把自签证书（`CN=smartquiz`）。

### 影响面
- 不同项目导出的 App **无法共存**，装新的直接覆盖旧的
- 无法通过升级机制识别为"同一个应用的不同版本"
- 后续若有更新/卸载逻辑会互相干扰

### 修复建议
- 包名按应用内容派生：`com.cjhtmldemo.<内容哈希前8位>`，或按应用名 slug 化
- 或开放为可配置项，允许用户指定
- 若要保留固定包名，则需在 UI 上明确告知"新包会覆盖旧应用"

> 注：证书 `CERT.RSA` 每次重签内容不同属正常现象（PKCS#7 含签名时间等），关键看**证书主体是否同一把** —— 实测为同一把。

## 四、🟠 P1-1 应用名长度限制按「字节」算，但提示按「字符」

### 现象
壳元数据里 `max_label_units: 22`。实测：
- **22 个 ASCII 字符 → 通过** ✅
- **8 个汉字 → 被拒**（判为超长）❌
- 7 个汉字（21 字节）→ 通过

### 根因
限制值 22 实际按 **UTF-8 字节数**计算，但错误提示用的是"字符"口径，用户会困惑（明明才 8 个字怎么就长了）。

### 修复建议
- 提示语改为「应用名最长 22 字节（约 7 个汉字）」
- 或前端输入框按字节实时计数并截断
- 或干脆放宽到主流启动器可接受的长度（中文 10~12 字）

## 五、🟠 P1-2 图标无尺寸下限校验

### 现象
**32×32 的极小图标被直接接受**，打包成功。装机后图标会被拉伸，糊成一团。

### 修复建议
- 加尺寸校验：`< 48×48` 直接拒绝并提示
- `< 192×192` 给出"可能不清晰"的警告
- 非正方形图标给出提示或自动居中裁剪

> 反面参考：这个导出器**做对了**图标魔数校验 —— 伪造的 `.png`（实为 JPEG 改名）被成功识破拒绝。

## 六、🟡 P2-1 多来源参数冲突时静默处理

### 现象
同时传入 `html_file` 与 `html_dir` 时不报错，实际取值优先级不明确 —— 实测出现「**正文内容取自 A 来源、图标却取自 B 来源**」的混搭情况。

### 修复建议
- 冲突时显式报错："请只指定一个来源"
- 或文档化明确优先级，并在返回值中回显实际使用的来源

## 八、📌 测试方法教训（重要）

上一轮做了 14 个测试包，全部通过"**静态拆包验证**"：

- 图标三条路径都正确替换 ✅
- 应用名成功写入 resources.arsc ✅
- libs 依赖齐备 ✅
- 载荷正确打入 ✅

**但一个都没做过真机安装。**

结果：**-124 这个"100% 必现、决定生死"的问题全程漏网**，直到真机安装才暴露。

👉 **后续回归必须把「真机安装 + 启动」纳入必测项**，静态拆包只能证明"包结构完整"，不能证明"包能装能用"。

## 九、修复优先级与顺序建议

| 优先级 | 问题 | 工作量 | 说明 |

| 🥇 1 | P0-1 arsc 未对齐 | 小 | 不修则 100% 装不上，必须最先解决 |
